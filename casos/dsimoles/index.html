DSimoles: a framework for design systems and the iMoles ecosystem DS

Two things are exposed here at once: DSBook, a reusable framework to define, document and track a design system, and DSimoles, the design system of the iMoles ecosystem for medical applications with WCAG 2.1 AA accessibility, built with that framework.

The starting point is the prototype from the iMoles project review: it provides the products, requirements and components the design system has to cover. The framework opens right here, in the browser, with all its content.

What is exposed

The DSimoles repository holds two layers that can be read separately: the method, and the system obtained by applying it.

Framework

DSBook

A workspace to define, document and track a design system, designed to be reused in other projects.

  • Definition guide with one subsection per decision and its acceptance criteria.
  • Tracking matrix with statuses (Ready, In process, Pending, Not applicable) and a recorded review.
  • Static HTML documentation container, with no build step or external services.
  • Workflow between Claude Design, Claude Code and Git, with protection against losing work.

Design system

DSimoles for the iMoles ecosystem

The design system for the medical applications of the iMoles ecosystem, defined with the framework.

  • Primitive and semantic tokens, with themes.
  • Base components and patterns, plus iMoles-specific product components (for example the risk badge, the capture row or the analysis summary).
  • WCAG 2.1 AA accessibility as a requirement, not an extra.
  • Governance: how something in the system is added, changed or deprecated.

Starting point

Where it comes from

The initial starting point is the prototype from the iMoles project review.

That navigable prototype of the dermatological pre-diagnosis app fixes the products, flows and requirements the design system has to serve. DSimoles does not start from a generic component catalogue: it starts from what that proposal needs and generalises it where it makes sense.

That is why base and iMoles-specific components live side by side in the system, and why the guide content (users, products, requirements) is written from that case.

How it works

The repository is the source of truth. Design and implementation are split between two tools and a person who validates.

  1. 1 GitHub. It is the only source of truth for the system.
  2. 2 Claude Design. Reads the repository, designs and builds the page for each section.
  3. 3 Claude Code. Brings the changes in, integrates them locally and runs the data-contract and test checks.
  4. 4 Validation. The responsible person reviews locally; nothing is pushed without their approval.
  5. 5 Record. Each integration is logged in the changelog and Claude Design is told to continue from the new base.

Status

Of the 175 subsections in the guide, 25 are Ready with a recorded review, 46 are in process, 1 is pending and 103 are marked not applicable, each with an explicit reason.

An existing page does not imply Ready: that status requires a recorded review, not an automatic certification.

Figures correspond to project version 0.29.0 (2026-10-15) and change with each integration.
